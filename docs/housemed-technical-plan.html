What the research found

The sample supports extracting structured product offers. The hard work is validating what each price actually buys.

01

Price tiers are embedded

All 21 sampled product pages included structured quantity-price offers. Read those offers, then check the visible price.

Read the technical detail+

Every sampled product page exposed a script[type="application/ld+json"] object with @type: Product, a product name, a source SKU, and one or more offers. Each observed offer had price, priceCurrency, eligibleQuantity.value, eligibleQuantity.unitCode, availability, and a product URL. Other JSON-LD objects described the pharmacy and corporation; a parser must select the Product object rather than the first script.

The visible interface consistently exposed an H1, SKU, stock status, total-price status, quantity radio group, and a custom numeric input named priceTierSelect. These are useful validation signals. Generated React element IDs are not suitable permanent selectors. The page also loads scripts from /_next/static/chunks/, which is evidence of a Next.js-based frontend, not a guarantee about its backend or API contracts.

The primary price example is Lisinopril 20mg: 30 tablets displayed $9.00, 90 displayed $12.60, and 180 displayed $18.00 during this session. The embedded offers agreed. The offer's nested UnitPriceSpecification repeated the total and its associated quantity; it did not turn $12.60 into a per-tablet price. Preserve the complete quantity-price pair and interpret this source's observed semantics. Schema.org's offer model describes the fields, but its field names alone do not establish a site's exact pricing implementation.

CHAPTER 02Proposed

Discover the catalog

Build a persistent inventory of the entire reachable public website, then select medication listings from that inventory. Verify website coverage independently through Codex browser control.

OUR OWN WEBSITE MAP · REQUIRED FOR MVP

Discover → record → revisit

Maintain crawl_pages for all reachable public page types: directories, products, editorial/help pages, and policies. Combine homepage navigation, header/footer links, pagination, product variants, and any usable published sitemap; pricing extraction targets a separate selected medication cohort.

One shared crawl_pages table, with a small navigation adapter for each source. No separate XML file or graph database is needed.
  1. Start from several entry pointsUse the homepage, header/footer navigation, every public category root, known URLs, and available HTML/XML sitemaps.
  2. Follow relevant links and page statesDiscover all public branches, subcategories, paginated results, content pages, and separate product variants. Keep page discovery broader than medication extraction.
  3. Remember what we discoverSave each normalized URL once per source, its first discovery origin, processing result, and next visit time.
  4. Keep the map growingRefresh known prices daily and discovery routes weekly initially. Newly found products enter the next bounded collection batch.
Required manual coverage audit through Codex browser control+

Use an independent browser traversal: begin at the live homepage, inspect the header and footer, expand every public navigation branch, and visit all category/subcategory directories and distinct directory pagination states. Include non-medication branches and public content/policy links. Compare the URLs and visible product links reached through this review with crawl_pages; do not merely reopen the crawler’s own URL list and call it comprehensive.

Use Codex browser control to inspect rendered menus, page ranges, visible product cards, variant controls, and loaded links. Review representative pages from every page template and branch. Record a branch checklist, visited URLs/page states, timestamps, expected URLs discovered in the browser, corresponding inventory IDs, and screenshots or DOM excerpts supporting each coverage decision. Every independently observed in-scope URL must have a correctly classified inventory row.

Pass condition: all public branches reached by the review are accounted for; every directory page state has been traversed; duplicate URLs and aliases are reconciled; displayed count discrepancies are explained; and there are zero unresolved missing pages, unclassified pages, or pending/blocked in-scope branches. A missing page sends the crawler back for correction and another audit of the affected branch. An unreachable in-scope branch leaves the gate incomplete; it is not silently excluded.

The scope report lists permitted hosts, explicit exclusions, unavailable discovery inputs, and the audit time. “Comprehensive” means comprehensive for the reachable public website at that time. Browser inspection cannot certify undisclosed URLs, authenticated content, or products never exposed through any accessible navigation or sitemap.

What the map contains — and what it cannot prove+

A published sitemap may omit pages. It reflects what its publisher includes. Link discovery supplies another route to products; a sitemap can also reveal pages that navigation misses. Google’s sitemap overview describes these complementary discovery methods.

For HealthWarehouse, incompleteness is a possibility, not a measured finding. We inspected its HTML category directory, but could not inspect the XML sitemap and have not completed a full category sweep. We cannot yet quantify missing products.

Our map represents observed pages within a defined scope, not a copy of the server’s directory tree. The same product can be linked from several categories; a root-level URL can still be a relevant medication. Store the first discovery origin on the page row and additional category/page observations in run evidence. A separate table for every link relationship is unnecessary in V1.

Unlinked pages that appear in neither a usable sitemap nor known navigation may remain undiscovered. A crawl that finds no new links has finished its reachable scope; it has not proved that every product on the website is covered.

Shared discovery logic, small adapters per source+

Shared mechanism: read configured seeds, deduplicate discovered URLs, persist the pending inventory, schedule due pages, record outcomes, and enforce crawl limits. Keep each source’s seeds and allowed hosts in its adapter configuration initially.

Source adapter: identify useful links, recognize page types, wait for rendered content, walk pagination, expose product variants, and extract source product IDs and offers. Start with explicit rules from inspected pages; we do not need an AI classifier or a universal crawler that guesses how every website works. A source with a usable catalog feed can supplement discovery and supply quotes. For MVP acceptance it does not replace the website inventory or the manual browser audit; selected pricing listings must still trace to inventoried product pages.

Normalize conservatively: resolve relative links and remove only known tracking or presentation parameters. Keep parameters that change product identity or results. Only discard fragments after verifying they are anchors, not application routes. Preserve path case and meaningful query values; validate redirects and canonical hints before merging URLs. In HealthWarehouse, ?qty=best is a presentation hint, while a different strength URL can identify a different product.

Separate URLs from product identity: deduplicate page rows by source and normalized URL. After extraction, distinct URLs with the same verified source SKU can point to one listing. Refresh the listing’s preferred validated product URL once per run instead of fetching every alias daily. Never merge distinct strengths merely because their names or paths resemble each other.

Handle stateful pagination explicitly: HealthWarehouse can show page 1 and page 2 at the same URL. Store one category URL in crawl_pages; track (category_url, page_index, page_size), page fingerprints, and discovered IDs in crawl_runs.checkpoint and run evidence. URL deduplication must not stop the remaining page states from being processed. Save newly discovered URLs before advancing the durable checkpoint; replay after interruption remains safe.

Keep each run bounded while preserving full-site scope: follow public internal page links across all configured source hosts, including non-medication retail and content branches. Private/account routes, cart/checkout flows, form submissions, external destinations, and binary/static assets are excluded explicitly; keep exclusion counts and reasons in run evidence. Respect robots directives and source limits. Include linked pagination and filters that expose unique products or pages; deduplicate equivalent sorting, tracking, and presentation states. Do not generate arbitrary search strings or combinatorial URL guesses. Page, depth, and time budgets pause work with pending states retained; they cannot turn an unfinished website crawl into a passed completeness gate.

How we measure coverage+

For each discovery run, record its seed set and scope, unique URLs discovered, new versus known products, completed versus pending category states, ignored links, failures, and blocked branches. Compare distinct product IDs with the source’s displayed counts as a diagnostic; counts can disagree, and categories can overlap.

Cross-check discovery paths: flag a product found through a usable sitemap but missed by its expected category sweep, or a curated medication search that reveals a new listing. Search is a bounded gap check, not an attempt to enumerate every possible query.

Report coverage as “all reachable public branches completed and independently browser-audited; N pages and M product URLs” or “partial; these public pages or branches remain pending or blocked.” Browser verification is a required acceptance step. It does not prove the existence or absence of undisclosed, unlinked, or private pages. An unchanged weekly discovery pass or an absent link does not justify deleting a listing or marking it out of stock.

Scope: the full reachable public website.

Inventory every reachable public HTML page within the source’s configured website hosts, including non-medication retail and editorial branches. Select the medication crawl sample only after this inventory passes the browser coverage audit. Discovery may require multiple resumable runs; the price-refresh budget does not cap the website inventory.

First discovery pass versus recurring price updates+

Discovery pass: combine the configured discovery paths, visit every discovered public branch, walk directory pagination, and collect unique page URLs plus product URLs/SKUs. Upsert discovered URLs into crawl_pages and save page-state checkpoints in crawl_runs. A product found in multiple categories should still be collected once per run. Use published categories and actual links rather than guessed URL combinations.

Product pass: open each selected product, extract its structured quantity-price offers, validate product identity and packaging, and update listings, offers, and changed offer_history. Several quantity offers can come from a single product page; not every quantity needs a separate page visit.

Recurring updates: revisit the known product URLs on the proposed daily refresh schedule. Recheck discovery routes weekly for new listings and changed links. Do not rediscover the whole site for every price refresh. An incomplete crawl never proves a product has been removed.

For the tested 224-item category with 24 results per page, a complete sweep would need 10 listing-page states, followed by the unique product pages selected for collection. We verified the transition from page 1 to page 2, not that full sweep. Both states used the same URL, so URL-only deduplication would miss later products.

Login, cart, checkout, patient records, prescription-management flows, and external advertising destinations remain outside discovery. Public non-medication retail, editorial, help, shipping, and policy pages belong in crawl_pages. They do not automatically become medication listings or price offers.

Read the technical detail+

One verified entry point is the public HTML sitemap, which exposed 649 anchor elements in this session. That figure includes duplicates and navigation links; it is not a count of products. Traverse all public website branches, including prescription, pet, insulin, supplies, personal care, toys, and editorial/help pages. Record every in-scope public page in the inventory, while restricting medication price extraction to eligible selected product listings. Account flows remain excluded.

Product listing anchors are identifiable by their visible product title and SKU. Capture their href, source category, source SKU, and the current listing page index. Starting prices can be stored as a diagnostic field, but must not enter the household-price calculation.

Category and search pages hydrate after the heading appears. Waiting for an H1 alone produced an incomplete view during this review. Wait for either a complete product-list state with pagination, an explicit empty result, or a documented error. Bound the wait and record failure; never treat a loading shell as an empty catalog.

In the tested category, the Next button changed 1–24 of 224 to 25–48 of 224 without changing the URL. The proposed discovery key is (category_url, page_index, page_size), not URL alone. Wait for the range and product fingerprint to change after each click. Persist the product IDs discovered on each page; stop when Next is disabled. Stop and flag a loop if a previously processed fingerprint repeats. Resume a failed category sweep by reopening the category and advancing to the checkpoint, unless a stable public pagination request is subsequently observed and validated. Do not invent ?page= URLs.

Category pages expose a page-size control set to 24. Its alternatives were not tested. Keep 24 initially. Changing view mode or page size is not a new category or product.

The search UI navigated to a search path containing the term. Its 27 results included metformin combinations and extended-release products. Search is a targeted supplement for a curated medication list and missing-product investigations; it is not evidence of exact identity or complete catalog coverage. A search navigation from FAQ retained /faqs in the canonical tag during the captured client session. For discovery pages, track the requested and final URLs independently of canonical metadata.

CHAPTER 03Proposed

Collect & validate

Each product is a bounded job. A price reaches the app only after identity, quantity, and freshness checks.

Ready to publish

  • Product identity matches the purchase panel
  • Quantity, currency, and total agree
  • Ordering unit and package content are resolved
  • Availability and last-checked time are recorded

Send for review

  • Wrong strength or conflicting identity
  • Unknown pack size or concentration
  • Visible price and structured price disagree
  • Blocked request, incomplete page, or stale result
Read the technical detail+

Use a clean, logged-out browser context, an ordinary browser configuration, and a single product navigation at a time. Browser access in this research session succeeded; initial unattended collection has since been tested on this Mac: HealthWarehouse access succeeded, while Cost Plus’s clean automated storefront returned 403. Test that deployment environment before committing to catalog-scale collection. A challenge response is an access failure, not a missing medication. The design should pause on challenges and must not depend on CAPTCHA solving, copied user-session cookies, or evasive proxy rotation.

Read all JSON-LD scripts and safely parse objects, arrays, and @graph containers. Select the Product whose name/SKU corresponds to the visible purchase panel. Restrict followed URLs to the known source origin; unexpected redirects become review events. Validate the final URL, product identity, and relevant canonical value together. Follow observed strength/brand controls as separate variants only when needed to discover listings absent from the category sweep. In the tested Lisinopril strength change, URL, H1, SKU, offers, and canonical all changed together.

Extract these source facts before any normalization: product name, exact SKU including punctuation, selected quantity, selected total, visible unit label, prescription-required state, stock state, offer quantities/totals/currency, package wording, and any explicit species/weight label. Store a small evidence payload containing the Product JSON-LD and purchase-panel fields, its hash, timestamp, and parser version. Do not copy clinical monographs, reviews, cookies, account content, or payment information into the pricing dataset.

Initially capture all explicitly represented quantity-price pairs rather than issuing a request for every possible quantity. On loose-unit products, the extra structured offer with quantity 1 may be a unit-price representation; do not advertise a one-tablet fill until the corresponding selection has been validated. On fixed packs, quantity 1 commonly is the actual package offer. Keep unit-price-only and unverified ordering quantities in source evidence until purchasability is validated; publish only validated ordering quantities to offers.

Validate every product's selected default against its corresponding embedded offer. On a rotating sample and after parser changes, select the smallest and largest advertised quantities and compare the displayed totals with the embedded data. If the two disagree after the page settles, quarantine that product's new observations. A custom quantity can be quoted only after observing its displayed total, or after a source-specific pricing rule is independently established. One successful 31-tablet example does not establish an interpolation formula for the entire catalog.

Conceptual job flow:

navigate to observed product URL
wait for coherent product identity and purchase panel
parse matching Product JSON-LD
validate SKU/name/currency/quantities/stock and default total
resolve ordering unit and package content, or flag ambiguity
save immutable source evidence first
commit listing, changed offer history, and current offers in one database transaction
mark the page result successful; query eligibility from current offer state and freshness

Semantic roles and labels are preferable to generated IDs for validation interactions, consistent with Playwright's locator guidance. Exact selectors are implementation details to test against saved fixtures and the deployment browser; this HTML remains the authoritative plan and acceptance record; implementation lives in the backend source files.

What happens when a crawler checks a price+
  1. New offer: insert the current offer and its initial history row in one transaction.
  2. Same validated offer: update last_checked_at and its successful run reference. Record the successful check in run evidence; do not duplicate the full history row.
  3. Price, availability, fees, eligibility terms, or source-expiry changes: update the offer and append the new version to offer_history atomically.
  4. Failed or ambiguous extraction: record the failure in the run. Leave the last valid offer and timestamp untouched; unresolved identities remain excluded from comparisons.

Serialize updates per offer or use row locks. Reject observations older than the current last_checked_at, so a slow earlier crawl cannot replace newer data. A unique run/offer history key makes retries idempotent. A price returning to a former value still creates a new chronological history row.

The history snapshot keeps the comparison context that existed at observation time. If a source reuses a product ID for a different drug or package, retire affected current offers and require identity review before publishing replacements. Do not relabel old history as the new product.

For a fully validated response, retire an offer that is explicitly no longer offered. A partial response, timeout, or challenge does not prove an offer disappeared. Freshness still depends on a recent successful check and any source expiration.

Run evidence lives in object storage and includes per-product results, matched offer keys, content hashes, and parse errors. This retains proof of unchanged checks without adding a large per-offer daily-check table. Start with one active worker per source and a run lock. The worker reads due pages from crawl_pages; run checkpoints preserve pagination progress and bounded worklists. Upsert discoveries before advancing the checkpoint. Add a separate queue only when actual parallel scheduling requires it.
